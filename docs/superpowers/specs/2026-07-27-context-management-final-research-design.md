# 上下文管理最终调研报告与讲稿设计

> 设计日期：2026-07-27
>
> 状态：已确认

## 1. 目标

基于现有 DeepEM 实现和已完成的外部项目调研，形成两份最终 Markdown 材料：

1. 一份可在组会上展示、也可会后归档审阅的完整技术调研报告；
2. 一份与报告章节对应、适合 20-25 分钟现场讲述的口语化讲稿。

核心调研对象限定为：

- Pi Agent（pi-mono）；
- OpenCode；
- OpenAI Codex CLI；
- Claude Code。

报告需要有源码或官方文档支撑，重点回答上下文管理、上下文压缩、触发时机、切分对象、压缩产物、持久化恢复、与 DeepEM 的差异及后续优化路线。

## 2. 受众与表达原则

听众了解 DeepEM 的业务背景，但不了解上下文管理实现细节。因此材料必须：

- 先解释上下文管理不等于摘要；
- 建立选择、预算、压缩、记忆、持久化和恢复的统一框架；
- 用 DeepEM 当前实现作为共同参照；
- 再进入外部项目的源码机制；
- 最后回到 DeepEM 的具体优化，而不是停留在项目介绍。

主报告采用技术文档风格，保留足够的机制、参数、源码路径和风险边界。讲稿采用口语表达，不逐段复述报告。

## 3. 交付文件

### 3.1 最终调研报告

路径：`docs/context_management_final_research_20260727.md`

职责：

- 保存完整论证和证据；
- 支撑组会展示；
- 支撑会后审阅、继续设计和实现；
- 成为后续上下文管理改造的统一研究基线。

### 3.2 组会讲稿

路径：`docs/context_management_final_research_speaker_notes_20260727.md`

职责：

- 控制总时长为 20-25 分钟；
- 与报告章节建立明确对应；
- 提供口语化讲述、转场和展示提示；
- 提供组会可能追问及简短回答。

不生成 Word、PPT 或 PDF。

## 4. 主报告叙事结构

采用“统一问题框架 + 项目完整深挖 + 横向收敛”的混合主线。

### 4.1 结论摘要

开头直接回答：

- 四个对象分别最值得借鉴什么；
- DeepEM 当前实现处于什么水平；
- 关键缺口是什么；
- P0/P1/P2 分别应做什么。

### 4.2 统一问题框架

明确区分：

- 上下文选择；
- token 预算；
- 工具结果压缩；
- 历史摘要；
- 运行状态；
- 长期记忆；
- 持久化与恢复。

统一使用以下问题研究四个对象：

1. 管理哪些上下文？
2. 什么时候压缩？
3. 依据什么预算或信号？
4. 压缩哪些对象？
5. 如何选择合法切点？
6. 压缩成什么？
7. 如何持久化和恢复？
8. 失败与质量边界是什么？

### 4.3 DeepEM 当前基线

介绍：

- `general/workspace` 上下文模式；
- 领域化工具结果压缩；
- `tool_result_id + path` 细节回捞；
- Reducer V2 的 65%/80%/90% 分级策略；
- history unit 和 tool pair 保护；
- 结构化语义摘要、缓存和增量摘要；
- 当前主要缺口和已知问题。

### 4.4 四个对象深挖

每个对象按相同问题模板组织，但突出不同代表能力：

- Pi Agent：压缩内核、合法切点、split turn、增量摘要和分支；
- OpenCode：真实 token 触发、序列化、session compaction event 和恢复投影；
- Codex：自动/手动/远程/token-budget 多路径、checkpoint、world state、resume/fork；
- Claude Code：自动与定向压缩、压缩后重注入、按需加载、subagent 隔离、记忆审计和用户控制面。

每章包含：机制闭环、代表参数/结构、失败边界、与 DeepEM 对比、可借鉴与不宜照搬。

### 4.5 横向比较

至少比较：

- 触发条件；
- 预算计算；
- 压缩单位和切点；
- 摘要格式；
- 工具关系保护；
- 原始细节保留；
- 增量摘要；
- 持久化与恢复；
- 当前状态重注入；
- 用户控制和可观察性。

### 4.6 DeepEM 优化路线

按优先级给出：

- P0：持久化 checkpoint、压缩事件、恢复投影、统一 ContextPolicy、上下文来源 trace、确定性回退；
- P1：手动/区间压缩、索引先行按需加载、会话分支、受控长期记忆；
- P2：高级检索、长期事实时间语义和专题试点。

每项建议说明来源机制、DeepEM 现状、改造价值、改动范围、风险和验证方式。

### 4.7 实验、风险和结论

覆盖：

- 简单通用问答延迟；
- 长工具会话压缩与恢复；
- 摘要失败回退；
- 信息保真和证据回捞；
- 页面切换/服务重启恢复；
- 长期记忆污染风险。

## 5. 讲稿设计

### 5.1 时间分配

| 时间 | 内容 |
|---|---|
| 0-2 分钟 | 调研背景、问题和结论预告 |
| 2-5 分钟 | 统一问题框架与 DeepEM 当前基线 |
| 5-15 分钟 | 四个对象，每个约 2.5 分钟 |
| 15-19 分钟 | 横向比较和关键发现 |
| 19-23 分钟 | DeepEM P0/P1/P2 优化路线 |
| 23-25 分钟 | 总结和讨论引导 |

### 5.2 每段固定结构

每段讲稿包含：

1. 时间和对应报告章节；
2. 这一段必须让听众记住的结论；
3. 可直接讲述的口语稿；
4. 报告展示位置或表格提示；
5. 进入下一段的转场语。

### 5.3 四项目讲述标签

- Pi Agent：最完整的压缩内核；
- OpenCode：压缩作为持久 session 事件；
- Codex：生产级压缩与恢复闭环；
- Claude Code：上下文治理的产品控制面。

### 5.4 预期问答

讲稿末尾准备以下问题：

- 为什么选择这四个对象？
- DeepEM 当前方案是否落后？
- 为什么不直接照搬 Codex/OpenCode？
- P0 改造量多大？
- 压缩是否会导致事实丢失？
- 简单问题延迟和上下文压缩是什么关系？
- 是否需要长期记忆或图数据库？

## 6. 证据规范

### 6.1 A 级：源码确认

Pi Agent、OpenCode、Codex 使用已记录的仓库快照、源码路径、结构和测试作为证据。具体参数必须与对应快照绑定。

### 6.2 B 级：官方公开

Claude Code 为闭源产品，只使用 Anthropic 官方文档确认产品行为。不得推断其内部 prompt、固定阈值、数据结构、模型选择和重试算法。

### 6.3 DeepEM 基线

DeepEM 结论以当前配置、实现文档、评测结果和已有设计报告为准，使用当前已启用的：

```text
DEEPEM_CONTEXT_SEMANTIC_COMPRESSION=1
DEEPEM_CONTEXT_REDUCER_V2=1
```

不得继续沿用“Reducer V2 未启用”的旧结论。

### 6.4 事实与建议分离

报告明确区分：

- 外部项目确认事实；
- 对行为的合理解释；
- 面向 DeepEM 的借鉴判断；
- 需要实验验证的假设。

## 7. 范围控制

AutoGen、Letta、Graphiti 不设置独立主章节。必要时仅用于说明策略接口、长期记忆和时序事实等关联机制，并注明它们来自扩展调研。

不包含：

- 泛泛的 Agent 行业综述；
- 与上下文管理无关的产品功能；
- 无法验证的闭源实现推断；
- 尚未进入近期路线的完整图数据库设计；
- 重复粘贴现有报告的大段文字。

## 8. 质量标准

最终材料必须满足：

1. 四个对象均完整回答统一八问；
2. 关键参数、文件路径和产品行为有来源边界；
3. DeepEM 比较使用当前实现；
4. 同一机制在不同章节中术语一致；
5. 报告结论能映射到明确的 P0/P1/P2；
6. 讲稿按正常语速可在 20-25 分钟完成；
7. 讲稿与报告章节、表格和结论一致；
8. 不存在占位符、未闭合代码块或错误章节引用；
9. 报告适合独立阅读，讲稿适合直接讲述；
10. 两份文件均只使用 Markdown。

## 9. 验证方法

- 检查 Markdown 标题层级、表格和代码块；
- 检索四个项目名称及统一问题覆盖情况；
- 核对 DeepEM 环境开关与阶段阈值；
- 核对源码 commit 和官方文档证据等级；
- 统计讲稿字数并按每分钟约 220-260 个中文字符估算时长；
- 对照报告与讲稿的章节引用和结论；
- 扫描占位标记、不确定措辞和无来源固定参数。
