# 上下文管理全景调研报告设计

## 1. 目标

新建一份以上下文完整生命周期为主线的调研报告，系统覆盖上下文选择、按需组装、隔离、状态生命周期、记忆治理、压缩以及可观测性。报告应明确：上下文压缩只是上下文管理中的一个环节，不能代替来源选择、状态恢复、事实治理和权限控制。

原报告 `docs/context_management_final_research_20260727.md` 保持不变，作为偏重上下文压缩机制的专题材料。新报告输出为：

`docs/context_management_lifecycle_research_20260727.md`

## 2. 读者与使用场景

读者了解 DeepEM 的业务流程，但不了解上下文管理内部实现。报告用于组会调研汇报和后续技术方案讨论，因此既要建立完整概念框架，也要落到 DeepEM 当前实现、差距、优先级和验证方法。

## 3. 调研对象与证据边界

继续以 Pi Agent、OpenCode、Codex CLI、Claude Code 为主要外部对象，并以 DeepEM 当前实现作为对照基线。

- Pi Agent、OpenCode、Codex CLI：使用既有固定源码快照和前序调研证据。
- Claude Code：只使用 Anthropic 官方公开文档，不推断内部阈值、摘要 Prompt、模型或持久化数据结构。
- DeepEM：以当前 `.env`、实现报告、评测报告和代码行为为准。
- 已确认事实、公开行为和面向 DeepEM 的建议必须明确区分。

## 4. 核心叙事

报告采用生命周期主线：

```text
问题与任务识别
  -> 上下文来源发现
  -> 选择、路由与按需加载
  -> 预算分配与输入组装
  -> 隔离、权限与来源边界
  -> 模型执行与状态事件
  -> 压缩、淘汰和细节回捞
  -> 会话持久化、恢复和分支
  -> 候选记忆提炼、验证、更新和失效
  -> 来源级观测、用户控制和持续评测
```

其中压缩章节保留必要深度，但不再逐项目重复展开全部阈值、切点、摘要模板和失败路径。详细压缩实现指向原专题报告。

## 5. 报告结构

1. 执行摘要：给出上下文管理定义、核心结论和 DeepEM 优先事项。
2. 调研范围与统一模型：说明证据等级、生命周期框架和关键对象。
3. DeepEM 当前全景：按来源、选择、组装、隔离、运行状态、压缩、记忆和观测梳理现状。
4. 上下文选择与按需组装：问题分类、general/workspace 路由、progressive disclosure、预算分配和动态工具加载。
5. 上下文隔离与权限边界：用户、会话、Case、工作区、工具、子任务和数据来源隔离。
6. 会话、任务和状态生命周期：session/run/turn/task 状态机、后台执行、页面恢复、checkpoint、resume、rewind 和 branch。
7. 记忆治理：工作记忆、情景记忆、语义事实、规则与偏好；写入、验证、更新、冲突、失效和审计。
8. 压缩与窗口预算：压缩在整体系统中的位置、四项目代表机制、DeepEM Reducer V2 和工具结果回捞；篇幅较原报告明显缩短。
9. 可观测性、用户控制与评测：来源级 token、策略 trace、生命周期事件、上下文面板、手动控制和分层指标。
10. 四项目横向比较：围绕完整管理维度比较，而非只比较压缩。
11. DeepEM 目标架构与路线：给出 P0/P1/P2、数据对象、接口边界和验收实验。
12. 风险、边界与结论。

## 6. 五个重点维度

### 6.1 上下文选择

说明“是否注入”优先于“注入后如何压缩”。覆盖意图分类、模式选择、相关性、权威性、时效性、成本和失败回退。以 DeepEM `general/workspace` 分流及其性能数据为核心案例。

### 6.2 记忆治理

区分原始记录、当前状态、短期工作记忆、长期事实、用户偏好和系统规则。长期记忆必须包含 owner、scope、source refs、confidence、verification status、valid time 和失效策略；模型推断先作为候选记忆，不直接升级为业务事实。

### 6.3 隔离

覆盖租户、用户、会话、任务、Case、设备、工作区、工具和子代理边界。隔离同时约束检索范围、工具权限、缓存键、持久化对象和可见性，不只依赖 Prompt 指令。

### 6.4 状态生命周期

将前端页面状态与后台任务真相解耦。说明 session、run、turn、task、event、checkpoint 的关系，以及 submitted、running、streaming、completed、failed、cancelled 等状态如何持久化和恢复。

### 6.5 可观测性

每轮记录上下文来源、选择原因、各来源 token、预算、工具 schema、压缩阶段、缓存命中、记忆命中、隔离域、checkpoint、回退和耗时。用户界面应提供模式、来源和任务状态的可理解展示，但不暴露内部思考过程。

## 7. 外部项目的角色

- Pi Agent：保留为压缩单元、合法切点、分支和结构化 handoff 的代表。
- OpenCode：重点转向 session projection、事件持久化和可恢复 compaction。
- Codex CLI：重点转向上下文管理器、world state、checkpoint、resume/fork 和生产级失败闭环。
- Claude Code：重点转向 progressive disclosure、规则与记忆分层、子代理隔离、用户控制和会话操作。

每个项目不再单独占据一整套重复章节，而是在对应生命周期环节中作为证据，并在横向比较章节集中总结。

## 8. DeepEM 建议边界

- P0：统一 ContextPolicy、来源级 trace、后端任务状态机、持久化 ContextCheckpoint、确定性恢复与隔离键。
- P1：索引先行按需加载、上下文面板、手动模式和分支、受控 memory blocks、后台研究上下文。
- P2：时序事实、冲突与失效治理、混合检索和小范围知识图试点。

不建议一次性引入全局长期记忆、让模型自动写入已确认事实，或用复杂检索替代正确的 general/workspace 路由。

## 9. 验收标准

- 原报告不被修改。
- 新报告形成完整生命周期框架，五个重点维度均有机制、项目实践、DeepEM 现状和建议。
- 压缩部分相对原报告明显精简，并明确链接原专题报告承接细节。
- 横向比较至少覆盖选择、组装、隔离、状态、记忆、压缩、恢复、可观测性和用户控制。
- 所有 Claude Code 结论遵守官方证据边界。
- 当前开关、65%/80%/90% 阈值和 general 模式性能数据与现有实现资料一致。
- Markdown 标题层级、表格和代码围栏有效，无 TODO、TBD 或占位段落。
